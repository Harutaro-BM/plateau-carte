何をするものか

PLATEAUを使って何かを分析しようとすると、最初に「自分の街のデータに必要な属性が入っているか」を調べることになる。 公式には属性情報公開リストがあるが、これは仕様上その属性が定義されているかの○×で、 実際に値が入っている割合ではない。

実測すると、両方向に食い違う。建築年が○のいわき市は51.3%、白河市は37.8%。 逆に空欄の宗像市は86.2%、北九州市は85.0%（いずれも2020年度データ同士の比較）。 ○だから使えるとも、空欄だから使えないとも言えない。

さらに、その公式一覧は56都市ぶんで、最終更新は2021年8月6日（PDF内に印字）。 PLATEAUは現在306自治体なので、残る250自治体には参照できる一覧そのものが無い。

カルテは306自治体すべてのCityGMLを実際に開いて数え、 「この街でこの分析を始められるか」を段階評価で返す。 「うまくいくか」は保証しない ── 属性が揃っていることは必要条件であって十分条件ではないため、 そこは主張範囲から外している。

データの流れ

入口は2つ。自治体名とCityGMLの所在を引くCKAN API、そして地図の境界に使う国土数値情報。 本体は縦一本のパイプラインで、carte.json が唯一の中間成果物になる。

なぜHTTPレンジ要求なのか

PLATEAUのCityGML zipは1自治体で200MB〜1GBあり、大半はDEMと浸水想定区域。必要なのは udx/bldg/*.gml だけ。 zipの中央ディレクトリは末尾にあるので、seek／read／tell をRangeリクエストで実装した ファイルライクを zipfile.ZipFile に渡せば、標準ライブラリだけで必要なメンバだけ取れる。 9.2MBのzipの一覧取得が転送0.84MBで済む。

測る8属性とダミー値

建物モデルから8つの属性を取り出す。厄介なのは、欠損がNULLではなく「値」として入っていること。 気づかずに平均を取ると壊れるので、充填率から除いている。

ダミー値の判定は scan.py の DUMMY 辞書と measure() にある。高さは数値判定で負値を除き、建築年は1800〜2100の範囲に入るものだけ数える。

用途bldg:usage461（不明）

建築年bldg:yearOfConstruction範囲外の年

「年度」は整備年度であって測量年ではない。 時系列で使うなら uro:surveyYear を見る必要がある。 同一年度に複数版が併存する自治体もある（海田町2021はv2とv3、更別村2023はv3とv4）。

段階評価と可否判定

なぜ小数を出さないのか

全メッシュを読むと306自治体で数十GBになるので、標本抽出が要る。 では標本のばらつきはどれくらいか ── 全市を読んだ5都市で市域を10帯に分けて充填率を測ったところ、 幅は1.6〜17.6ポイントだった。

「94% 対 19.8%」の桁の差を判定するには十分だが、「94.1% 対 91.3%」の順位付けには足りない。 だから出力は段階評価にしている。自分の測定の誤差を測ったうえで、 その誤差に埋もれない粒度を選んだということ。

段階の境界は scan.py の grade()。
記号充填率意味
◎90%以上ほぼ全棟に入っている
○60〜90%実用に足りることが多い
△20〜60%用途を選べば使える
▲0〜20%ほぼ使えない
×0%1棟も入っていない

4つの分析の可否

充填率から「で、何ができるのか」を導く。ここがカルテの値打ちで、判定条件は derive() にある。

いずれも必要条件。満たしても結果の精度は保証しない。人口推定を実際に走らせた5都市の中央値誤差は6.4%〜41.0%に開いた。
分析条件理由該当
時系列比較測量年 60%以上年度＝整備年度なので測量年が要る276
高さ解析高さ 90%以上 かつ 高さ種別 60%以上軒高か最高高さか分からないと使えない228
人口推定用途 60%以上 かつ 階数 60%以上用途で住宅を特定し、階数で床面積を作る188
耐震・被害推定建築年 40%以上 かつ 構造種別 60%以上新耐震の前後と、木造か非木造か98

4つすべてが「可」なのは61自治体、どれも始められないのが14自治体。

地図の作り方

表では「埼玉36」としか言えないものを、絵にする。 背景は47都道府県の輪郭で、その上に306自治体を段階色で塗る。 県境が見えることが目的なので、県単位への融合は省けない。

  • 境界は国土数値情報 N03（2025年1月1日版）。zipの .geojson メンバだけをレンジ要求で取る（1県あたり約4.5MB、全国で154MB）
  • 融合と単純化はDuckDB spatialの ST_Union_Agg と ST_SimplifyPreserveTopology
  • 幅1000pxで日本全体（経度約18度）を描くと1px≒0.018度なので、県輪郭は0.012度、自治体は0.005度まで単純化する
  • 出力は素のSVG。依存ライブラリなしという性格を崩さない
  • 沖縄は位置だけ移動し、縮尺は本土と同じにした。変えると那覇市の大きさを他と比べられなくなる
  • 小笠原村はPLATEAU整備済だが北緯27度で本土の縮尺を壊すため、図示せず地図上に注記した

47県で23分、転送154MB。中間の map_geom.json が684KB、出力SVGが411KB。

走らせ方

# 1. 自治体コードと日本語名の対応を取る（306件）
python scripts/names.py

# 2. 全国走査。約75分・転送4.7GB。途中保存があるので中断しても続行できる
python scripts/scan.py

# 3. 地図。約23分・転送154MB。境界はディスクにキャッシュされる
python scripts/build_map.py
python scripts/render_map.py

# 4. ビューアを開く（依存ライブラリなし）
python -m http.server --directory web

走査は途中保存があるので、中断しても同じコマンドで続きから走る。 すでに status: "ok" の自治体は飛ばす。

検証の仕組み

走査をやり直すたびに、スライドやビューアに古い数字が残る。目視では必ず見落とすので機械で照合する。 実際にこの2本が、目で見て気づかなかった不具合を見つけている。

応募前に両方を通す。どちらかが赤なら提出しない。
検査何を見るか見つけた実例
check_deck.py スライドの数値を carte.json から再計算して突き合わせる ビューア本体に古い「305自治体・2,381,135棟」が残っていた
check_overflow.mjs 全19枚について、要素が枠の下端を超えていないか 10枚目の画像が枠を40px超えてフッタに重なっていた

主張から外したもの

「属性が下流の推定を改善する」ことの実証は2回試して2回とも成立しなかった。 1回目は計測震度を全域一定と仮定して支配要因を欠き、順序が逆転。 2回目は震度メッシュを入れて n=18 では並んだが、n=33 に増やすと崩れた。再現しないので使わない。

建築年の値そのものの正しさも検証を試みたが、公的リストが建物名で識別するのにPLATEAUに名称が無く、 街区内の突合が別々の建物を同一に潰した。測っていたのは突合方法の質だった。これも外した。

限界

  • 標本である。1自治体あたり建物数の多い3メッシュしか読んでいない。市域全体の充填率とは1.6〜17.6ポイントずれうる
  • 値の正しさは測っていない。入っているかどうかだけ。建築年が1877年と書いてあってもそれが正しいかは別の話
  • 必要条件でしかない。属性が揃っていても分析が成立するとは限らない。用途91.3%の中央区で人口推定の誤差は33.2%だった
  • 実測日が固定されている。PLATEAUは毎年度拡大するので、時間が経つほど古くなる。再走査は75分でできる
  • ランキングにはしない。◎○△×を「成功予測」と誤読させるUIにはしない

使う側だけでなく整備する側にも返る。建築年が入る117自治体は県単位で固まっているので、 実測は「どの発注仕様が充填を生んだか」を指す材料になる。
