# 標本設計の入れ替え（2026-08-30）

別セッションの指摘（`INCOMING-2026-08-30.md`）を受けて、
`scan.py` の抽出方式を **上位k件 → 決定的な層化抽出** に変えた。
検証の経緯は [03-sample-bias.md](03-sample-bias.md)。

## なぜ変えたか

旧方式は「非圧縮サイズの大きいメッシュを3件」。
これは「アルファベット順の先頭を取ると市域の縁を引いて建物0件になる」問題への
正しい対策だったが、**充填率を系統的に上振れさせる**と分かった。

サイズが大きいメッシュは建物が密な市街地で、属性はそこに整備されている。

### メッシュ数を増やすだけでは直らない

鉾田市（全235メッシュ・66,699棟を実測。真値 階数 5.0%）:

| 方式 | 推定 | 誤差 | 読む棟数 |
|---|---:|---:|---:|
| top-3（旧） | 71.7% | 66.7pt | 3,446 |
| top-8 | 32.4% | 27.5pt | 7,620 |
| top-16 | 21.6% | 16.7pt | 12,975 |
| top-24 | 16.0% | 11.1pt | 17,509 |

**棟数の26%を読んでも真値の3倍。**上位から取る限り直らない。
鉾田市は235メッシュ中**上位3つにしか属性が入っていない**（4番目で既に0.0%）ため。

## 新方式：決定的な層化抽出

1. 建物GMLを**非圧縮サイズ順**に並べる（zipの中央ディレクトリだけで分かる。ダウンロード不要）
2. **総バイト数が等しくなるよう4層**に切る（件数で等分すると巨大メッシュが1層に偏る）
3. 各層から**等間隔に6件**（計24件）取る。**乱数を使わない**ので誰が走らせても同じ
4. 層ごとに充填率を出し、**層の総バイト数の比で合成**する

```
推定充填率 = Σ_層 (層の総バイト数 / 全バイト数) × (層の標本の充填率)
```

### なぜ重みにバイト数を使えるか

1棟あたりバイト数が自治体内で安定しているため。
鉾田市の235メッシュで **8,000〜11,000バイト/棟**に収まる。
つまりサイズは棟数の代理変数になる。

なお当初は「属性が入った建物ほどバイト数が大きいので、
サイズで選ぶこと自体が属性の入ったメッシュを選ぶことに近いのでは」と疑ったが、
**1棟あたりバイト数と充填率の相関は r=0.041 で無相関**だった。この仮説は外れている。
サイズが大きいのは1棟が重いからではなく、単に棟数が多いから。

## 設計の選定（5自治体の全メッシュ実測に対する成績）

鉾田市・下田市・柏市・町田市・郡山市の全メッシュを読み、
どの抽出方式でも机上で評価できるようにしたうえで比較した（`sim_sampling.py`）。

| 設計 | k | 誤差平均 | 最悪 |
|---|---:|---:|---:|
| top（旧） | 3 | 21.0pt | 66.7pt |
| top | 24 | 5.6pt | 11.8pt |
| 系統抽出のみ | 24 | 3.1pt | 6.4pt |
| 層化＋乱数 | 8 | 3.1pt | 22.5pt |
| 層化＋乱数 | 24 | 2.0pt | 17.0pt |
| **層化＋等間隔** | **24** | **0.9pt** | **2.8pt** |

層内を乱数で取ると seed に依存する。
**再現性を主張する作品で抽出が seed で変わるのは筋が悪い**ので、等間隔（決定的）を採った。
成績も等間隔のほうが良い。

## 走らせて踏んだ罠（2026-08-30）

### ディスクを埋めて135自治体ぶんを失った

`parse_bldg.py` はGMLメンバをディスクにキャッシュする。
同じ都市を何度も解析するときには有効だが、
**全国走査は1メッシュを1度しか読まないのでキャッシュに意味がない。**

306自治体 × 24メッシュで **5,695ファイル・104GB** に達し、
Cドライブが100%になって走査が落ちた。

対処：`parse_bldg.USE_CACHE` スイッチを追加し、`scan.py` の冒頭で切る。

```python
pb.USE_CACHE = False
```

### 保存が既存ファイルごと壊した

`save()` は `write_text` で直接書いていた。
`write_text` は開いた時点でファイルを切り詰めるので、
**書き込み中にディスク満杯になると carte.json が0バイトになる。**
5自治体ごとに保存していた進捗も、まとめて失われた。

対処：一時ファイルに書いてから `replace` で置き換える。

```python
tmp = DATA / "carte.json.tmp"
tmp.write_text(...)
tmp.replace(DATA / "carte.json")
```

**「途中保存があるので中断しても続行できる」と謳っている以上、
その保存自体が壊れない作りでなければ意味がない。**

## 旧新の差分（`scripts/diff_grades.py`）

標本の取り方を変えれば段階は動く。**どれだけ動いたかを示せないと差し替えの根拠にならない**ので、
旧（上位3メッシュ、`carte_top3_2026-08-19.json`）と新（層化抽出）を突き合わせる。

### キー名を取り違えて「変化なし」を捏造しかけた

最初の実装で `grade` のキーを `height` / `yearBuilt` / `structure` / `surveyYear` と書いた。
実際のキーは `measured_height` / `year_of_construction` / `structure_type` / `survey_year`。

`.get(k)` が `None` を返し、それを

```python
if a is None or b is None:
    continue        # ← これが致命的
```

で飛ばしていたため、**4項目が比較されないまま「変化0件」と表示された。**
比較総数が 267×3 にしかなっていないことに気づかず、
「変化は用途と階数だけ」と誤った結論を出した。

対処：欠損時は `continue` せず停止する。

```python
if a is None or b is None:
    raise SystemExit("段階が取れない: %s %s ..." % (code, k))
```

**欠損を黙って飛ばす実装は、欠損を「異常なし」に化ける。**
充足率を測るツールでこれをやると、測っている対象そのものを見誤る。

### 結果（267件時点・走査完了後に再取得）

| | 件数 | 割合 |
|---|---|---|
| 変化なし | 1,989 | 93.1% |
| −1段階 | 123 | 5.8% |
| −2段階 | 2 | 0.1% |
| +1段階 | 22 | 1.0% |

下方修正125件に対し上方22件。**旧方式は充足率を過大評価していた。**
上位3メッシュは密集市街地に偏り、属性が整備された区画を優先的に拾っていたため。

項目別では 用途54 / 階数32 / 計測高22 / 測量年20 / 建築年19 件が変化。
構造・耐火・LOD1高は0件で、これはメッシュによらず一律に整備／未整備だから動かない。
